# 训练终端无输出问题排查与修复

> 记录时间：2026-06-27  
> 影响范围：点击「开始训练」后终端卡在"训练已启动，等待输出..."，GPU 占用率为 0，训练进程实际未运行

---

## 现象描述

在训练页面点击「开始训练」后：
- 终端显示"训练已启动，等待输出..."后再无任何日志输出
- 系统 GPU 占用率始终为 0%，未见 CUDA 活动
- 状态栏一直显示"训练中"，但实际无任何训练在进行
- 无报错、无异常提示，完全静默

## 根因分析

### 致命 Bug：`bufsize=0` + `read1()` 不兼容

问题出在 `train_manager.py` 中子进程启动与日志读取的配合上：

```python
# train_manager.py 原代码

# 启动子进程时设置 bufsize=0
self._proc = subprocess.Popen(
    [python_path, "-u", RUNNER_PATH, args_json],
    stdout=subprocess.PIPE,
    stderr=subprocess.STDOUT,
    bufsize=0,       # ← 问题根源①：产生原始 FileIO 流对象
    env=env,
    ...
)

# 读取线程中使用 read1()
def _reader_loop(self):
    ...
    try:
        while True:
            chunk = stream.read1(4096)  # ← 问题根源②：FileIO 没有 read1 方法！
            ...
    except Exception:
        pass  # ← 问题根源③：异常被静默吞掉，无任何提示
```

### 技术细节

| 项目 | 说明 |
|------|------|
| `bufsize=0` 的效果 | Python `subprocess.Popen` 的 `stdout` 变为原始的 `io.FileIO` 对象（无缓冲二进制流） |
| `read1()` 的归属 | `read1()` 是 `io.BufferedReader` 独有的方法，`FileIO` **不具备此方法** |
| 实际异常 | `AttributeError: 'FileIO' object has no attribute 'read1'` |
| 异常处理 | 被 `except Exception: pass` 静默吞掉，无任何日志或提示 |

### 连锁反应（管道死锁）

```
read1() 抛出 AttributeError
        ↓
except Exception: pass 静默吞掉
        ↓
读取线程立即退出死亡
        ↓
无人消费 stdout 管道中的数据
        ↓
子进程输出塞满 Windows 管道缓冲区（约 65KB）
        ↓
操作系统阻塞子进程的 write() 系统调用
        ↓
训练子进程永远卡在第一条 print() 语句上
        ↓
GPU 永远不会被使用，训练永远不会开始
```

> **关键**：这是一个经典的 **管道死锁（Pipe Deadlock）** 问题。父进程不读管道 → 子进程写满管道后被 OS 阻塞 → 双方互相等待，形成死锁。

---

## 解决方案

### 修复①：移除 `bufsize=0`，使用默认缓冲

```python
# 修复后
self._proc = subprocess.Popen(
    [python_path, "-u", RUNNER_PATH, args_file],
    stdout=subprocess.PIPE,
    stderr=subprocess.STDOUT,
    # 不再设置 bufsize=0
    # 默认 bufsize=-1，stdout 为 BufferedReader，支持 read1()
    env=env,
    ...
)
```

- 默认 `bufsize=-1` 时，`proc.stdout` 是 `io.BufferedReader` 对象
- `BufferedReader.read1(n)` 方法：从底层流读取最多 n 字节，至少等待 1 字节即返回
- 配合 `-u` 参数（子进程侧无缓冲），实现真正的实时输出

### 修复②：异常不再静默吞掉

```python
# 修复后
except Exception as e:
    err_msg = f"\n[ERROR] 日志读取线程异常：{e}\n"
    self._buffer.append(err_msg)
    self._broadcast(err_msg)  # 错误信息直接显示在终端上
```

### 修复③：子进程参数改用文件传递

原来通过命令行参数传递 JSON 字符串，在 Windows 下路径中的反斜杠和引号会被 cmd.exe 转义破坏：

```python
# 原代码（有风险）
args_json = json.dumps(args, ensure_ascii=False)
subprocess.Popen([python_path, "-u", RUNNER_PATH, args_json], ...)

# 修复后（安全）
args_file = os.path.join(project, ".dataset_split", f"train_args_{name}.json")
with open(args_file, "w", encoding="utf-8") as f:
    json.dump(args, f, ensure_ascii=False, indent=2)
subprocess.Popen([python_path, "-u", RUNNER_PATH, args_file], ...)
```

## 经验教训

1. **永远不要用 `except Exception: pass` 吞掉异常** —— 至少打印到日志，否则问题无法定位
2. **`bufsize=0` 与 `read1()` 不兼容** —— 需要 `read1()` 就必须用默认缓冲（`BufferedReader`）
3. **Windows 管道缓冲区只有约 65KB** —— 必须及时消费子进程的 stdout，否则必然死锁
4. **pywebview (WebView2) 对 SSE 支持不可靠** —— 桌面应用应优先使用短轮询方案
